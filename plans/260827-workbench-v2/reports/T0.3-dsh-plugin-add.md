# T0.3 — `dsh plugin --profile <name> add <spec>` 支持的 spec 形态

## English summary

`dsh plugin add` is **not** limited to local `file:`/TGZ paths. Reading the shipped
CLI (`@deepseek-ai/dsh@0.1.1-rc.2`, package directory `apps/cli`) shows the `plugin`
subcommand is a thin `pnpm add` forwarder: it `spawnSync("pnpm", args, { cwd: profileDir })`
with the user's arguments passed through almost verbatim. It therefore accepts every
spec form `pnpm add` accepts — npm registry `name`/`name@version`/`name@range`, tag
specs, `npm:` aliases, `git+`/`github:` specs, remote tarball URLs, and local
`file:`/`link:`/bare paths (`.tgz`) — not merely local tarballs. The one CLI-level
transform, `anchorPathSpec`, only rewrites *relative* dot-paths (`.`, `..`, optionally
prefixed `file:`/`link:`) against the invoking directory; absolute paths, registry
names, and URLs pass through untouched. No custom integrity/hash verification exists
in the `dsh`/`dsh-app-boot` install path beyond whatever `pnpm` itself does via its
lockfile. This session did not execute the command at runtime — the conclusion rests
on static code reading plus pnpm's well-documented `add` spec grammar (pnpm `11.9.0`,
pinned in this repo's `packageManager` field).

---

## 结论

**`dsh plugin --profile <name> add <spec>` 支持 npm registry spec(`name`、`name@version`、
`name@range`、`name@tag`、`npm:alias@version`),也支持 git spec(`git+...`、`github:...`)、
远程 tarball URL、以及本地 `file:`/`link:`/裸路径 `.tgz`——并不是"仅支持 file:TGZ 本地路径"。**

原因:`dsh plugin` 子命令的实现是一个**极薄的 pnpm 转发层**——它把 `add` 之后的全部参数
(除了对**裸相对路径**做一次锚定重写)原样传给 `pnpm add`,在 profile 目录下以子进程方式
执行。也就是说,`dsh plugin add` 能接受的 spec 集合 = `pnpm add` 能接受的 spec 集合。当前
仓库固定的 pnpm 版本是 `pnpm@11.9.0`(见 `package.json:7` 的 `packageManager` 字段),这是
pnpm 自 v1 起就稳定支持的核心语法,不存在版本兼容性问题。

需要单独说明的现实约束(不是代码层面的限制,而是发布状态的限制):
`@deepseek-ai/dsh-workbench`(或其发布名)目前**没有发布到 npm registry**,因此虽然机制上
`dsh plugin add <name>@<version>` 是可行的调用形态,但**今天没有任何已发布的 registry 包可供
该形态解析**——A4 文档如果要用 Release-first 路径(下载不可变 TGZ),就必须用 `file:`/裸路径
这一支 spec,而不是 npm registry spec。见下方"对 A4 的建议"。

### 3. 唯一的参数改写:`anchorPathSpec`——只动裸相对路径,其余原样透传

```
90: function anchorPathSpec(argument, cwd) {
91: 	const match = /^(?<prefix>(?:file|link):)?(?<path>\.{1,2}(?:[/\\].*)?)$/.exec(argument);
92: 	if (match?.groups?.path === void 0) return argument;
93: 	return `${match.groups.prefix ?? ""}${resolve(cwd, match.groups.path)}`;
94: }
```
(plugin-9h8shc4d.js:90-94)

以及其上方的说明注释:

```
79: * Rewrite relative filesystem specs against the user's invoking directory.
80: * pnpm runs with cwd = the profile directory, so a bare `.` or `../plugin`
81: * (or their `file:`/`link:` forms) would silently resolve inside the profile
82: * — `add .` from a plugin checkout would self-link the profile. Absolute
83: * specs, registry names, and every other pnpm argument pass through
84: * untouched.
```
(plugin-9h8shc4d.js:79-84)

正则只匹配"以 `.` 或 `..` 开头(可选 `file:`/`link:` 前缀)"的参数;npm registry 名字
(如 `foo` 或 `foo@1.2.3`)、绝对路径(如 Windows 的 `C:\...`)、URL、`git+...` 等一律不
匹配,原样传给 `pnpm`。这与仓库现有文档已经实际使用的写法一致:

`docs/INSTALL.md:88`:
```
dsh plugin --profile web add file:C:\absolute\path\to\dsh-workbench\dist\wanyexin1998-dsh-workbench-0.2.0-rc.1.tgz
```
这是一个**绝对路径 + `file:` 前缀**的 spec,`anchorPathSpec` 的正则不匹配它(因为路径部分
不是以 `.`/`..` 开头),因此原样透传给 `pnpm add` —— 与源码分析结论一致。

## 对 A4 文档安装命令形态的直接建议

Release-first 默认路径(下载不可变 TGZ + `dsh plugin add`)应该继续使用**本地
`file:` + 绝对路径**的 spec 形态,而不是 npm registry spec 形态,原因有两条,一条是
"必须",一条是"更优":

1. **必须**:包目前没有发布到 npm registry,`dsh plugin add <name>@<version>` 这种
   registry spec 在机制上虽然被接受,但今天没有对应的已发布包可供解析,会直接报错。
2. **更优**:tasks.md §1 已经把"下载 → 校验 SHA256(对照 `SHA256SUMS`)→ 安装"定为
   五要素之一的既定顺序;本地 `file:` spec 天然贴合这个顺序——用户先下载 TGZ 到本地、
   核对哈希,再执行安装命令,安装这一步不会替用户去发起任何网络请求。如果改用
   `pnpm add <release-url>.tgz` 这种直接 URL spec(pnpm 也支持,但本报告未在本次任务
   范围内对其做静态代码验证,纯属 pnpm 通用能力认知),会让"先校验再安装"这一步失去
   意义(pnpm 会自己发起下载,校验发生在下载之后已经太晚,或者需要额外的二次校验设计)。

建议 A4 沿用仓库现有文档(`docs/INSTALL.md:88`)已经验证过的命令形态,只是把版本号/文件
名换成 rc.2 的产物名:

```
dsh plugin --profile web add file:<下载后 TGZ 的绝对路径>
```

Windows 下绝对路径形如 `file:<DOWNLOADS_DIR>\wanyexin1998-dsh-workbench-0.2.0-rc.2.tgz`;
macOS/Linux 形如 `file:<DOWNLOADS_DIR>/wanyexin1998-dsh-workbench-0.2.0-rc.2.tgz`。`<DOWNLOADS_DIR>`
即当前用户下载目录的绝对路径(Windows 下位于用户主目录下的 `Downloads` 子目录;
macOS/Linux 下位于用户主目录下的 `Downloads` 子目录)。
由于该 spec 是绝对路径,`anchorPathSpec`(plugin-9h8shc4d.js:90-94)不会对其做任何改写,
文档里怎么写就会怎么执行,不存在"用户当前目录不同导致路径解析到别处"的隐患;这也是它比
"裸相对路径"(如 `add ./dsh-workbench.tgz`,需要用户在下载目录下执行命令才安全)更适合写进
面向最终用户的复制粘贴命令的原因。

`file:` 前缀本身不是必需的(pnpm 也接受裸 `.tgz` 路径),但保留它能让读者一眼看出这是一个
本地文件 spec 而不是 registry 包名,建议 A4 沿用现状,不做形态改动。
